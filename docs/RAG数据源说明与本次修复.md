## 一、两个数据源，各走各的管线

| 数据源 | 内容 | 谁在用 | 存放位置 |
|---|---|---|---|
| **原始 wiki 页面** | 三款游戏的剧情正文（对白、任务流程、章节目录） | **路径 C：剧情问答 RAG** | `.workbuddy/rag_index.json`（索引） |

也就是说：

- 你在「剧情问答」里问「41 长路归航讲了什么」→ 检索的是**战双 wiki 抓下来的正文**

两者目前**互不流通**。要不要把评价也接进问答检索，见第五节。

## 二、「搜索什么都是无结果」的两个根因

### 根因 1：索引被测试覆盖，只剩 33 块

诊断时索引状态：

```
chunks: 33      ← 正常应为 1900+
games: {原神: 21, 鸣潮: 8, 战双帕弥什: 4}
```

`_pages` 清单显示**每款游戏只有 1 个正文页**，其余全是目录卡片。

原因：`test_server_api.py` 的重建接口测试用 `maxPages=1` 重建了整个索引，
**直接覆盖了生产索引**。每跑一次测试，索引就退化成"目录卡片 + 1 页正文"。

### 根因 2：鸣潮正文此前完全没抓（错误结论）

之前代码里写着：

> 库街区为 SPA，暂无公开正文接口，仅索引目录卡片

**这个结论是错的。** 实测发现词条正文有公开 JSON 接口：

```
POST https://api.kurobbs.com/wiki/core/catalogue/item/getEntryDetail
参数：id=<entryId>          ← 关键：参数名是 id，不是 entryId
正文：data.content.story.<节点ID>.flow.raw[].content
```

- 用 `entryId=` → `code=2031 当前词条不存在`
- 用 `id=` → `code=200`，返回 20 万字符的词条数据

踩坑点：`flow` 是 **dict**（`{"raw": [...]}`）而不是 list，
按 list 迭代会拿到字符串键并静默返回 0 片段（这个问题让第一次集成测试全部判为"无正文"）。

## 五、待你决策：要不要把「剧情评价」也接进问答？

技术上很简单（把 `剧情记录数据.json` 作为第四个数据源加入索引即可），但要注意：

- 目前该文件里**只有 1 条记录**（`p-41`），纳入后检索意义有限
- 评价是主观短文本，wiki 是客观长正文，混在同一索引里可能**互相稀释召回**
- 更稳妥的方案：作为**独立数据源 + 前端加一个「仅搜我的记录」开关**

建议先多记录几条再决定。
